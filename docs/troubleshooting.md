# 구현에서 확인한 문제 해결

코드·후속 SQL·테스트에서 확인한 사례입니다. 초기 커밋에 이미 다수 migration이 포함되어 있어 파일명 날짜를 실제 장애 발생일로 해석하지 않았습니다. 운영 중 발생한 시간·피해 규모·개선 수치는 별도 확인이 필요합니다.

# 1. 승인 재처리와 레슨권 전환 이후 취소 복구

## 상황

같은 대기 요청을 여러 번 승인하거나, 마지막 1회를 승인해 다음 권이 활성화된 뒤 잘못된 승인을 취소할 수 있습니다. 단순히 현재 사용권에 1회를 더하면 다른 권의 잔여를 바꾸게 됩니다.

## 원인

승인 상태·사용수·다음 권 활성화는 서로 연결된 변경입니다. 기록과 차감을 따로 저장하면 일부만 반영될 수 있으며, 취소 기준을 현재 활성권으로 잡으면 원래 권을 복구하지 못합니다.

## 해결 과정

승인 RPC가 회원별 advisory lock과 행 잠금을 획득한 뒤 기록 상태를 다시 읽습니다. `pending`일 때만 일일 슬롯과 사용권을 검사하고 승인·차감합니다. 취소 RPC는 승인 기록의 `lesson_pass_id`로 원래 권을 찾습니다.

다음 권이 아직 미사용이면 대기로 되돌리고 원래 권을 활성화합니다. 다음 권을 이미 사용했다면 원래 권은 대기로 복구하여 active권 하나 제약을 유지합니다. 일괄 처리는 건별 성공·미처리 결과를 반환합니다.

## 최종 해결

DB 함수 안에서 승인·차감·권 전환·이력 저장을 처리하고, 취소 사유와 수행자를 남깁니다. 반복 승인·반복 취소·일일 제한·원래 권 복구에 대한 pgTAP 테스트가 있습니다.

- [승인·취소 RPC](../supabase/migrations/20260811000000_lesson_approval_workflow.sql)
- [현재 승인 함수](../supabase/migrations/20260816000000_remove_member_pause_management.sql)
- [업무 흐름 테스트](../supabase/tests/database/lesson_approval_workflow.test.sql)

**남은 검증:** 테스트 존재를 실제 다중 연결 동시성 검증으로 해석하지 않습니다. 등록·수동 조정은 다른 advisory lock 키를 쓰므로 모든 경로가 직렬화된다고 단정하지 않습니다.

## 배운 점

취소는 현재 값에 대한 단순 가감보다 원래 처리 대상의 식별이 중요합니다. 업무 규칙을 화면뿐 아니라 DB의 상태 재검사·제약과 함께 구현해야 다른 입력 경로도 같은 기준을 따를 수 있습니다.

# 2. 하루 두 번째 QR 요청이 막히던 조건 수정

## 상황

DB 승인 규칙은 하루 최대 2회인데 초기 QR 요청 함수는 첫 승인 이후 재요청을 막았습니다. 직접 등록과 QR 등록의 허용 범위가 달랐습니다.

## 원인

초기 `request_checkin`의 조건은 당일 `approved` 기록의 존재 여부였습니다. 1회와 2회를 구분하지 않고 `already_approved`를 반환했습니다.

## 해결 과정

후속 migration에서 당일 승인 건수를 계산하고 2건 이상일 때만 요청을 중단하도록 바꿨습니다. 첫 승인 뒤 요청은 `second_created`로 구분하고 화면에 추가 차감 안내를 제공합니다. 대기 요청이 이미 있으면 기존 요청을 반환하는 보호는 유지했습니다.

## 최종 해결

최신 `request_checkin`은 첫 요청·두 번째 요청·상한 도달을 나누고 현재 활성권 잔여도 반환합니다. pgTAP은 세 번째 요청이 새 기록을 만들지 않는 조건을, Vitest는 두 번째 요청 안내를 확인합니다.

- [두 번째 QR 요청 변경](../supabase/migrations/20260824000000_allow_second_daily_qr_request.sql)
- [최신 QR 함수](../supabase/migrations/20260825000000_checkin_result_remaining_count.sql)
- [DB 요청 테스트](../supabase/tests/database/checkin_dashboard.test.sql)
- [화면 결과 테스트](../src/lib/checkin/types.test.ts)

## 배운 점

같은 업무를 수행하는 QR·직접 입력 경로의 규칙을 비교해야 합니다. 요청 가능 여부와 승인 가능 여부는 각각 검증하되 일일 한도는 같은 운영 기준으로 맞춰야 합니다.

# 3. 과거 승인 당시의 잔여 횟수 보존

## 상황

승인 목록과 기록 화면에서 과거 처리 결과를 확인할 때, 이후 승인·수동 조정으로 달라진 현재 잔여가 당시 잔여처럼 보일 수 있습니다.

## 원인

`lesson_passes.used_count`는 현재 값입니다. 과거 승인 기록과 연결하더라도 그 시점의 사용·잔여 횟수가 자동으로 복원되지는 않습니다.

## 해결 과정

기록에 `pass_total_count_at_approval`, `pass_used_count_after_approval`, `pass_remaining_after_approval`을 추가했습니다. 승인으로 바뀌는 시점에 트리거가 차감 후 권 정보를 읽습니다. 과거 입력도 승인 INSERT이므로 같은 트리거를 사용합니다.

기존 승인 이력에는 현재 잔여와 이후 승인 건수를 이용한 역산 SQL을 추가했습니다. 이후 권 수정과 기록 조회는 분리하고 화면은 기록의 스냅샷을 읽습니다.

## 최종 해결

새 승인부터는 처리 직후 잔여를 별도로 보존합니다. 합계 일치 CHECK가 있고 기록·승인 화면이 해당 컬럼을 사용합니다. 기존 기록 역산은 과거 조정·취소 이력이 완전히 반영되는지 검증이 필요합니다. 전용 스냅샷 동작 테스트는 확인되지 않았습니다.

- [스냅샷 컬럼·트리거](../supabase/migrations/20260820000000_store_lesson_approval_pass_snapshot.sql)
- [기록 조회](../src/app/lesson-records/page.tsx)
- [승인 조회](../src/app/approvals/page.tsx)

## 배운 점

현재 상태와 사건 당시의 상태는 다른 데이터입니다. 정정 가능한 업무에서는 이벤트 시점의 값을 남겨야 하며, 사후 역산한 값과 당시 저장한 값의 신뢰도도 구분해야 합니다.

# 4. 레슨권 수정 RPC의 횟수 타입 불일치

## 상황

관리자 레슨권 수정 함수가 `smallint` 매개변수로 만들어진 뒤, 별도 migration에서 해당 서명을 삭제하고 `integer`로 다시 정의되었습니다.

## 원인

JavaScript의 수치는 DB의 `smallint`와 같은 타입을 직접 표현하지 않습니다. SQL 테스트도 정수 리터럴 `5`, `8` 등을 넘기므로 함수 호출의 정수 타입 해석과 기존 서명이 맞지 않을 수 있습니다. 실제 오류 로그는 저장소에 없어 운영 장애 여부까지 확정하지 않았습니다.

## 해결 과정

외부 매개변수를 `integer`로 바꾸고 내부 조정 차이는 범위 검증 후 `smallint`로 변환합니다. 0～8 범위와 필수 수정 사유·관리자 권한 검사는 유지했습니다.

## 최종 해결

최신 함수 서명은 `admin_edit_lesson_pass(uuid, date, integer, text, text)`입니다. DB 테스트는 잔여 수정·0회 소진·다음 권 활성화와 권한 차단을 검사합니다.

- [초기 함수](../supabase/migrations/20260823000000_admin_edit_lesson_pass.sql)
- [타입 수정](../supabase/migrations/20260823010000_fix_admin_edit_lesson_pass_count_type.sql)
- [권 수정 테스트](../supabase/tests/database/lesson_pass_edit.test.sql)
- [서버 호출·입력 검증](../src/app/lesson-passes/actions.ts)

## 배운 점

DB 저장 타입과 외부 호출 타입은 같은 선택일 필요가 없습니다. 호출 경계는 일반 정수로 받고 실제 업무 범위를 검증한 뒤 저장 타입으로 변환하는 방식이 호환성과 제약을 함께 유지합니다.
